## 二、用户发送图片/文件

### 2.1 入口

输入框左侧新增「📎」按钮，点击弹出系统文件选择对话框，支持多选，最多 5 个文件。

### 2.2 附件预览

选择文件后，输入框上方出现预览区：
- 图片：缩略图 + 文件名 + 大小 + 删除按钮
- 非图片：文件图标 + 文件名 + 大小 + 删除按钮
- 多个附件横向排列，超出换行
- 可单独移除某个附件

### 2.3 文件类型处理

| 类型 | 判断依据 | 处理方式 |
|------|---------|---------|
| 图片 | png/jpg/jpeg/gif/webp/bmp | 转 base64，以视觉 API 的 image_url 格式发送，气泡中显示缩略图 |
| 文本文件 | txt/md/py/js/json/html/css/yaml/csv 等 | 读取内容，拼入消息文本，前面加文件路径标记 |
| 其他文件 | 不匹配以上 | 只发送文件名和大小，提示 AI 无法直接读取此格式 |

### 2.4 限制

| 限制项 | 值 | 说明 |
|--------|---|------|
| 单个文件大小 | 5MB | 超过提示用户压缩 |
| 同时附件数量 | 5 个 | 超过提示用户 |
| 文本文件截断 | 50KB / 1000 行 | 和现有逻辑一致 |
| 图片 base64 payload | 实测上限 | 5MB 图片 base64 后约 6.7MB，需测试各 API 对单条消息大小的容忍度，过大时提示用户压缩图片 |

### 2.5 附件保存到历史的策略

**重要：** 图片附件保存对话历史时，只记录文件路径和元信息（文件名、大小），不存 base64 字符串。原因：
- 一张 2MB 图片 base64 后约 2.7MB
- 10 张图片就是 27MB，严重影响历史加载速度和搜索性能
- 加载历史时不再显示图片缩略图，改为显示文件信息卡片（文件名 + 大小 + 「图片已过期」提示）

### 2.6 气泡显示

用户消息气泡中如果有附件，在文字上方显示：
- 图片附件：缩略图（最大 200px 高），下方文件名和大小
- 文件附件：图标 + 文件名 + 大小

### 2.7 后端需要的能力

| 能力 | 说明 |
|------|------|
| 文件选择对话框 | 系统原生，支持多选，限制 5 个 |
| 图片转 base64 | 读取文件并编码 |
| 文件类型判断 | 按扩展名分类 |
| 文件信息获取 | 名称、大小、类型 |
| 文本文件读取 | 复用现有 read_file 逻辑 |

### 2.8 前端改动

| 改动 | 说明 |
|------|------|
| 📎 按钮 | 输入框左侧 |
| 附件预览区 | 输入框上方，动态渲染 |
| sendMessage 改造 | 检查附件，组装消息格式 |
| 用户气泡改造 | 支持显示附件 |
| 历史气泡改造 | 图片附件改为文件信息卡片 |

## 三、AI 发送图片/文件

### 3.1 AI 标记格式

AI 在回复中使用 `<!--file:send:path=...-->` 标记（HTML 注释格式，避免与代码块冲突）：

```
分析完成，生成了图表：

<!--file:send:path=outputs/chart.png-->
```

支持单个回复中包含多个 `<!--file:send:path=...-->` 标记，后端用正则 `<!--file:send:path=(.+?)-->` 解析所有匹配，前端依次渲染。

**为什么用 HTML 注释格式：** 三个反引号的代码块格式可能与 AI 回复中正常的代码块内容冲突（比如 AI 讲解 file:send 语法时）。HTML 注释在渲染时不可见，且不会与 markdown 代码块产生歧义。

### 3.2 处理流程

```
AI 流式回复完成
  ↓
后端解析回复中的所有 <!--file:send:path=...--> 标记
  ↓
逐个处理：
  ├── 读取文件（路径安全检查，必须在工作目录内）
  ├── 图片 → 转 base64 → 前端渲染图片预览
  └── 其他 → 返回文件信息 → 前端渲染文件卡片
  ↓
同时复制每个文件到用户配置的接收目录
```

**处理延迟：** 文件在整个流式回复结束后才处理，长回复时用户需要等待。前端应在文件渲染前显示一个「正在处理文件...」的 loading 占位，避免内容突然插入导致布局跳动。

### 3.3 气泡显示

**图片：** 气泡内直接显示图片预览，下方文件名和大小，附下载按钮。

**文件：** 气泡内显示文件卡片（图标 + 名称 + 大小 + 下载按钮）。

**多个文件：** 按顺序纵向排列。

### 3.4 保存到历史

AI 发送的图片同样只保存文件路径和元信息，不存 base64。加载历史时显示文件信息卡片。

### 3.5 接收目录配置

设置面板新增一项：
- 标签：「文件接收目录」
- 输入框 + 浏览按钮 + 「打开目录」按钮（用系统文件管理器打开）
- 提示：「AI 发送的文件会自动保存到此目录」

config.json 新增 `receive_dir` 字段。默认值为 MeClaw 目录下的 `downloads/` 文件夹。目录不存在时自动创建。

### 3.6 后端需要的能力

| 能力 | 说明 |
|------|------|
| 解析 file:send 标记 | 正则匹配，支持多个 |
| 图片转 base64 | 复用用户发送的逻辑 |
| 文件信息获取 | 名称、大小、类型 |
| 复制文件到接收目录 | shutil.copy |
| 路径安全检查 | 必须在工作目录内，防 ../ 越界 |

### 3.7 前端改动

| 改动 | 说明 |
|------|------|
| onStreamDone 改造 | 新增 file:send 解析和渲染（支持多个） |
| 图片渲染 | 在气泡中插入图片预览 |
| 文件卡片渲染 | 在气泡中插入文件下载卡片 |
| 设置面板 | 接收目录配置项 |
| 历史气泡改造 | AI 图片改为文件信息卡片 |

## 四、深度思考控制（含 DeepSeek 专属优化）

### 4.1 核心问题

不同模型厂商对「深度思考」的 API 参数格式完全不同：

| 厂商 | 思考开关格式 | 思考强度格式 | 参数位置 |
|------|-------------|-------------|---------|
| DeepSeek | `thinking: {type: "enabled/disabled"}` | `reasoning_effort: "high/max"` | thinking 在 extra_body 内，reasoning_effort 在顶层 |
| 通义 QwQ | 不同格式 | 不同字段 | 不同位置 |
| MiMo | 又不同 | 又不同 | 又不同 |
| 通用 OpenAI | 可能不支持 | `reasoning_effort`（不一定有效） | 顶层 |

如果都按 DeepSeek 格式发给其他模型，要么报错要么被忽略。反过来按通用格式发给 DeepSeek，深度优化就浪费了。

### 4.2 解决方案：API 配置层增加「模型优化」选项

在 API 配置编辑中新增一个下拉选项：

```
── API 编辑 ──────────────────────────────

别名：    [DeepSeek              ]
Base URL：[https://api.deepseek.com/v1]
API Key： [sk-xxxxxxxxxxxx       ]
模型名称：[deepseek-chat         ]

模型优化：[DeepSeek ▾]
  说明：选择对应厂商可获得更深度的参数优化

上下文上限：[65536            ]
```

**下拉选项：**

| 选项 | provider 值 | 说明 |
|------|------------|------|
| 通用（默认） | `generic` | 标准 OpenAI 兼容格式，最大兼容性 |
| DeepSeek | `deepseek` | DeepSeek 专属深度优化 |

选择 DeepSeek 后，弹窗底部显示一行提示：「已启用：深度思考 / 联网搜索 / 流式推理」，让用户知道选这个 provider 后解锁了什么能力。

### 4.3 config.json 中 API 配置

```json
{
    "id": "deepseek",
    "name": "DeepSeek",
    "base_url": "https://api.deepseek.com/v1",
    "api_key": "sk-xxx",
    "model": "deepseek-chat",
    "provider": "deepseek",
    "max_context": 65536
}
```

新增 `provider` 字段。

### 4.4 深度思考参数（DeepSeek 实际格式）

开启思考：
```json
{
    "reasoning_effort": "high",
    "extra_body": {"thinking": {"type": "enabled"}}
}
```

关闭思考：
```json
{
    "extra_body": {"thinking": {"type": "disabled"}}
}
```

**关键规则（来自 DeepSeek 官方文档）：**
- 思考模式下 `temperature`、`top_p` 等参数设置后不报错但不生效
- `reasoning_effort` 只有 `high` 和 `max` 有效，`low`/`medium` 会被映射为 `high`
- 默认 effort 为 `high`，复杂 Agent 场景自动 `max`

### 4.5 Bot 编辑弹窗联动

Bot 编辑弹窗的显示内容根据关联的 API 配置的 `provider` 动态变化：

**provider = "generic"（通用）时：**
```
✅ 基础设置（头像、名称、API、模型、温度、最大token）
✅ 灵魂文件夹
✅ 技能选择
❌ 不显示深度思考设置
❌ 不显示联网搜索设置
```

**provider = "deepseek" 时：**
```
✅ 基础设置（温度在思考模式下灰掉）
✅ 灵魂文件夹
✅ 技能选择
✅ 深度思考（开关 + 强度）
✅ 联网搜索
```

provider 为 generic 时，`thinking_enabled` 和 `thinking_depth` 字段仍然保存在 config 中（用户可能以后切换 provider），但后端构建 payload 时忽略它们。

### 4.6 深度思考 UI

```
── 深度思考 ──────────────────────────

深度思考：  [○ 关闭]  [● 开启]

思考强度：（仅开启时显示）
  [● 标准(high)]  [○ 深度(max)]

⚠️ 开启深度思考时，Temperature 设置不生效
```

- 关闭：发送 `thinking: {type: "disabled"}`
- 开启：发送 `thinking: {type: "enabled"}`
- 强度标准(high)：推荐日常使用
- 强度深度(max)：复杂推理和 Agent 场景
- 开启时 Temperature 输入框灰掉 + 提示文字
- Max Tokens 旁提示：「建议设置较大值，思考过程会占用部分 token」

### 4.7 reasoning_content 回传规则

来自 DeepSeek 官方文档的关键要求：

| 场景 | reasoning_content 是否需要回传 |
|------|------|
| 普通对话（无工具调用） | **不需要**，API 会忽略 |
| 有工具调用的轮次 | **必须回传**，否则 400 报错 |

**对 MeClaw 的影响：**

Phase 2 的文件操作（AI 使用 file: 标记）本质上就是工具调用。如果 DeepSeek 开了思考模式并且 AI 执行了文件操作，必须把 reasoning_content 保留在对话历史中并在后续回传。

**同理：** Skill 指令中如果引导 AI 使用文件操作标记，也会触发工具调用，同样需要保留 reasoning_content。

**实现策略：**

保存历史时：始终保存 reasoning_content（用于前端展示和历史回看）。

构建 messages 发送给 API 时：
- 普通对话轮次：去掉 reasoning_content
- 工具调用轮次（消息中有 `file:` 标记的）：保留 reasoning_content

**具体实现：** 当前 `build_messages_for_api` 中对每条消息做 clean 时，增加判断：
```python
for m in non_system:
    clean = {"role": m["role"], "content": m["content"]}
    # 判断是否为工具调用轮次：content 中包含 file: 标记
    if m.get("reasoning_content") and _has_file_ops(m.get("content", "")):
        clean["reasoning_content"] = m["reasoning_content"]
    messages.append(clean)
```
`_has_file_ops` 检查 content 中是否包含 `file:create`、`file:edit`、`file:delete`、`file:send` 等标记。这个判断逻辑应在 Step 3 就实现，不要留到后面。

### 4.8 后端 payload 构建逻辑

```
获取 bot 和关联的 profile
  ↓
判断 provider 类型

provider == "deepseek"：
  ├── thinking_enabled = true：
  │   ├── 发送 reasoning_effort = "high" 或 "max"
  │   ├── 发送 extra_body = {thinking: {type: "enabled"}}
  │   └── 不发送 temperature（不生效）
  │
  ├── thinking_enabled = false：
  │   ├── 发送 extra_body = {thinking: {type: "disabled"}}
  │   └── 发送 temperature
  │
  └── web_search = true：
      └── 合并到 tools 数组（注意和未来 function calling 的兼容）

provider == "generic"：
  ├── 发送 temperature
  └── 不发送任何特殊参数

通用逻辑：
  ├── 发送 max_tokens
  └── 构建 messages 时处理 reasoning_content 回传
```

### 4.9 tools 字段兼容性

DeepSeek 的联网参数是 `tools: [{type: "web_search"}]`。未来如果要支持真正的 function calling（工具调用），tools 数组需要同时包含联网搜索和其他工具：

```json
{
    "tools": [
        {"type": "web_search"},
        {"type": "function", "function": {"name": "...", ...}}
    ]
}
```

当前 Phase 4.5b 没有 function calling，只需要处理联网，但代码结构要预留合并能力。

## 六、Skill 技能系统

### 6.1 什么是 Skill

一个 Skill 是一个**可插拔的能力模块**，本质是一个文件夹，包含一组指令文档，告诉 AI「怎么完成某类任务」。

**与灵魂文件夹的关系：**
- 灵魂文件夹定义「这个人是谁」（身份、性格、记忆）
- Skill 定义「这个人会做什么」（能力、方法、模板）
- 两者叠加使用，互不冲突

### 6.2 Skill 文件夹结构

```
MeClaw/skills/
├── code-review/
│   ├── skill.json
│   └── instructions.md
├── api-generator/
│   ├── skill.json
│   ├── instructions.md
│   └── templates/
│       └── api_template.py
└── writing-assistant/
    ├── skill.json
    ├── instructions.md
    └── examples/
        ├── good_email.md
        └── bad_email.md
```

### 6.3 skill.json

| 字段 | 必填 | 说明 |
|------|------|------|
| id | 是 | 唯一标识，与文件夹名一致 |
| name | 是 | 显示名称 |
| version | 是 | 版本号 |
| description | 是 | 一句话描述 |
| icon | 是 | emoji 图标 |

### 6.4 工作原理

```
用户在机器人编辑中启用若干技能
  ↓
每次发送消息时，后端读取该 Bot 已启用的所有技能
  ↓
把每个技能的 instructions.md 内容拼接到 system prompt 中
  ↓
AI 读到这些指令后就知道怎么执行对应的任务
  ↓
如果技能中有 templates/ 或 examples/，
AI 可以通过文件读取操作访问这些文件
```

### 6.5 与 Bot 的关系

- 每个 Bot 独立维护自己启用的技能列表
- 同一个技能可以被多个 Bot 启用
- Bot 配置中新增 `enabled_skills` 字段（技能 ID 数组）

### 6.6 技能选择器 UI

**入口：** 机器人编辑弹窗中新增「技能」区域。

```
── 技能 ──────────────────────────────

☑ 📝 代码审查 v1.0
  审查代码质量、安全漏洞和性能问题

☐ 🔌 API 生成器 v1.2
  快速生成 RESTful API 代码

☑ ✍️ 写作助手 v0.8
  帮助撰写各类文档

☐ 📊 数据分析 v0.5
  分析 CSV/JSON 数据并可视化

[打开技能文件夹]
```

**交互规则：**
- 点击整行切换启用/禁用
- 已启用项左侧金色边框高亮
- 「打开技能文件夹」按钮 → 用系统文件管理器打开 skills/ 目录
- 没有任何技能时显示：「暂无技能，将技能文件夹放入 skills/ 目录后刷新」

### 6.7 System Prompt 组装顺序

1. 灵魂文件夹内容（soul.md → constraints.md → memory.md → knowledge/ → 其他 .md）
2. 已启用的技能指令（每个技能的 instructions.md）
3. 文件操作指引（固定的系统指令）

**上下文占用提示：** 状态面板中应显示 skill 指令占用的 token 量（估算），让用户清楚启用多个 skill 对上下文的影响。如果 skill 指令总量超过 10KB，在状态面板给出警告。

### 6.8 内置技能

首次运行时自动创建「📝 代码审查」示例技能，默认禁用。用户可参考其结构创建自己的技能，也可删除。

## 十四、注意事项

| 项目 | 说明 |
|------|------|
| provider 联动 | Bot 编辑弹窗必须根据关联 API 的 provider 动态显示/隐藏高级设置 |
| thinking 参数格式 | 必须用 DeepSeek 实际格式（extra_body），不能用假想格式 |
| reasoning_effort 只有两档 | high 和 max，low/medium 会被映射为 high |
| reasoning_content 回传 | 有 file: 操作的消息必须保留 reasoning_content，否则 DeepSeek 400 报错。用 `_has_file_ops` 判断 |
| Skill 与工具调用 | Skill 指令中引导 AI 使用文件操作也会触发工具调用，同样需要保留 reasoning_content |
| temperature 不生效 | 深度思考开启时 temperature 无效，UI 必须灰掉并提示 |
| tools 字段兼容 | 联网和未来 function calling 共用 tools 数组，代码结构要预留合并能力 |
| 图片历史保存 | 只存路径不存 base64，避免历史文件膨胀 |
| 图片 base64 大小 | 5MB 图片 base64 后约 6.7MB，需测试 API payload 上限 |
| 文本文件截断 | 50KB / 1000 行，和现有逻辑一致 |
| 路径安全 | AI 的 file:send 和 file:edit 路径必须在工作目录内 |
| file:send 标记格式 | `<!--file:send:path=...-->`（HTML 注释，避免与代码块冲突） |
| 接收目录 | 默认 MeClaw/downloads/，不存在时自动创建，设置面板有「打开目录」按钮 |
| 技能指令长度 | 每个 skill 的 instructions.md 建议不超过 2KB，状态面板显示总 token 占用 |
| 搜索性能 | 百级会话量本地读取无压力 |
| 搜索结果上限 | 50 条 |
| 搜索防抖 | 300ms |
| 搜索跳转 | scrollIntoView block: 'center' 居中显示目标消息 |
| 消息高亮 | 1.5 秒后恢复 |
| 多选删除不可撤销 | 确认弹窗醒目，删除按钮红色 |
| 删除当前活跃会话 | 自动切换到列表第一个，没有则自动新建 |
| 切换 Bot | 自动保存当前会话，自动新建会话关联新 Bot |
| 内置技能 | 只在首次运行时创建，用户删除后不恢复 |
| emoji 兼容 | 部分 emoji 在 Windows 上可能显示为黑白 |
| 最少 Bot 数量 | 1 个，不允许删除最后一个 |
| 最少 Profile 数量 | 1 个，不允许删除最后一个 |
