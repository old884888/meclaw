## 4. 学习脑 = 自进化（未来工作，依赖基础设施）

**确认定位**：学习脑就是「自进化」的载体，但**现在不做**，因为它依赖尚未引入的基础设施：

- **Skill 管理系统**（技能 / 提示词模板的注册与调度）
- **工具集 / 函数调用**（MCP、function calling 等）
- 候选闭环：`信号 → 候选 → 人工/自动确认 → 写回 L1 / Soul / Skill`

现有 `mnemos-learner-brain` spec 已规定「**只产候选、不自动改 soul.md**」，这是正确的安全基线。
**自进化排在 skill / 工具集落地之后**，届时学习脑才有「可被进化的对象（技能/工具/人格）」。

依赖关系：

```
工具集 / MCP / 函数  ─┐
Skill 管理系统       ─┼─→ 学习脑闭环（自进化）
记忆内核（阶段1-2）   ─┘
```

## 5. 八维 / 前额叶 的定位（诚实判断）

### 八维（MBTI 认知功能）—— 放「人格层」，不碰记忆内核
- 它描述的是**人格风格的权衡**（一个强另一个弱），属于**表达层**。
- **不提升命中率，不提升持久性**，但能让 Bot 的口吻 / 关注点 / 决策风格更立体。
- 落点：给每个 Bot 一个**八维权重向量**（如 `Ti:0.8, Fe:0.3, Ne:0.6…`），存人格配置；
  组装 prompt 时转成风格指令注入 persona 块（`persona_brain.py`），可进一步影响左脑思考框架措辞。
- 优先级：**阶段 4 锦上添花**。仿生学没错，但要分清：记忆仿**海马体**，八维仿**性格**，别混在一层。

### 前额叶（元认知 / 规划控制器）—— 谨慎，按需触发
- 现 `router.py` 是**零成本规则路由**（优点：不烧钱）。
- 真前额叶 = LLM 控制器，决定「要不要查记忆 / 要不要多步推理 / 要不要反问」，**每轮多一次 LLM 调用**，成本与延迟翻倍。
- 建议：**内核换完、命中率上来后再做**，且做成**复杂任务才触发的可选脑**，不是每轮。

### 7.1 PoC 实测（2026-06-25，官方 50 题，DeepSeek）

环境变量开关的探针（`embedding_poc.py` / `rerank_poc.py`，默认 off），模型：
embedding = `paraphrase-multilingual-MiniLM-L12-v2`，rerank = `BAAI/bge-reranker-base`。

| 题型 (n) | Baseline 哈希 | 仅 embedding | embedding+rerank |
|------|------:|------:|------:|
| 总体 | 66.0% | 66.0% | 60.0% |
| generalizing (8) | 62.5% | 87.5% | 50.0% |
| recommendations (7) | 85.7% | 28.6% | 71.4% |
| recall_facts (8) | 75.0% | 75.0% | 87.5% |
| reasons (10) | 60.0% | 60.0% | 50.0% |
| suggest_ideas (8) | 62.5% | 62.5% | 37.5% |
| evolution (9) | 55.6% | 77.8% | 66.7% |

**结论：**

- ✅ 真 embedding 提升语义/演变题（sanity：「过敏」↔「能吃虾」cos=0.518，哈希≈0）。
- ✅ Reranker 修复裸换 embedding 造成的精度回退（推荐题 28.6%→71.4%），**证明 P2 Reranker 为必需项**。
- ❌ 50 题样本太小，**不能据此判定总分**，需 200+ 题。

报告文件：`tests/benchmark/personamem/data/report_poc_*.json`。

## 10. 外部范式借鉴：我们该吸收什么

> 来源：`知识工程项目思维差异对比分析.md`、`Agent时代知识工程深度解析.md`。  
> 核心结论：我们在「记忆检索」侧已经走到前面了，真正值得吸收的是 **Hermes/Skillify 的执行经验沉淀机制**，而不是照搬“捕获一切”。

### 10.1 先说结论：哪些值得吸收，哪些不值得

| 来源 | 值得吸收 | 不建议照搬 |
|------|----------|------------|
| LLM-Wiki | Markdown 作为人机双可读载体；渐进式结构化 | 把所有知识都退回纯文本，不做结构化 |
| Obsidian-Wiki | 关系视角；知识不是列表而是网络 | 强行上复杂图谱，拖慢主线 |
| GBrain | 输入侧“先捕获再整理”的意识 | `Capture Everything` 全量吞入，拉低信噪比 |
| Hermes / Skillify | Skill 层、Nudge 触发、Curator 版本化、分层加载、安全审核边界 | GEPA / RL 重型进化现在就上，超出当前定位 |

一句话：**该学的是“经验如何变成可复用能力”，不是“把一切都存下来”。**

### 10.2 与现有系统的映射

```text
Hermes / 资料里的四层                 我们当前系统
────────────────────────────────────────────────────────
L1 Prompt Memory                  ≈  soul + constraints + L3 persona
L2 Session Search                 ≈  L0/L1 + hybrid/embedding recall
L3 Skills                         ≈  P6b `skills/`（approved 才注入）
L4 Honcho 用户建模                ≈  L3 persona profile（轻量版）

Nudge / Review / Curator          ≈  P6a nudge 规则 + 候选 API + manual approve
GEPA / RL                         ≈  暂无，且当前不建议优先做
```

这意味着：

1. **记忆检索主线并不落后**，甚至比资料里的“普通 Session Search”更强。  
2. **最大缺口不是 recall，而是 skill 层缺失**。  
3. learner 现在像“收件箱”，还不是“复盘工厂”。

### 10.3 设计原则：吸收这些“武功秘籍”时要守什么

#### 原则 A：记忆和技能分层，不再把所有经验都压成 L1 原子

L1 适合存“事实 / 偏好 / 约束 / 演变”；  
Skill 适合存“流程 / 步骤 / 踩坑 / 适用条件 / 失败征兆”。

如果继续把“怎么做事”也硬塞进 L1，会出现两个问题：

- 召回时混淆事实和流程，降低信噪比
- 同一个任务经验会碎成很多原子，无法整体复用

#### 原则 B：前台响应，后台沉淀

任何“复盘 / 提炼 / 合并 / 归档”都不能阻塞聊天主路径。  
这和现有 learner 规范完全一致，也与 Hermes 的思路一致。

#### 原则 C：自动产候选，人工决定生效

这是我们已经守住的安全边界，必须继续坚持：

- 自动采集信号：可以
- 自动生成候选 Skill / Prompt / L3 建议：可以
- 自动覆盖 `soul.md` / 自动启用 Skill：**不可以**

#### 原则 D：渐进加载，不让 Skill 库拖垮 token

Skill 层一定要复用我们已有的预算纪律：

- 默认不常驻全量加载
- 只按 query / task / topic 检索 top-k
- 命中不足时再回退到 L1/L2/L0

#### 原则 E：允许遗忘和合并，别把“持久”误解成“永不清理”

资料里很值得学的一点，是“约束驱动提炼”：

- 超过容量阈值就归并
- 重复经验要压缩
- 冷知识要降级

我们现在有“写入”和“召回”，但“巩固/遗忘”还很弱，这块正好是海马体类比里缺的那一半。

### 10.4 建议新增的三个提案方向

#### 提案 1：`mnemos-skill-memory`

**目标**：补齐 Skill 层，让“执行经验”有独立载体，不再挤在 L1 里。

**定位**：

- 面向“怎么做”的复用知识
- 属于热数据和冷数据之间的“温数据”
- 由 learner / curator 维护，但不自动生效

**建议存储形态**：

```text
souls/<bot>/skills/
  skill_xxx.md
  index.json
```

**单个 Skill 建议结构**：

- `title`：技能名
- `when_to_use`：适用任务 / 触发条件
- `steps`：推荐流程
- `pitfalls`：常见踩坑
- `signals`：失败征兆 / 风险提示
- `examples`：成功或失败样例
- `source_sessions`：来源会话
- `status`：pending / approved / archived / superseded

**注入策略**：

- 常规对话：不加载 Skill
- 任务型对话：先召回 Skill top-k，再决定是否注入
- 若 Skill 命中弱，回退到 L1/L2 记忆

**收益**：

- 把“会做事”从记忆系统中独立出来
- 后续学习脑有了明确可进化对象
- 任务型 bot（教学、写作、编程、分析）复用率提升

**非目标**：

- 不做跨 bot 共享市场
- 不做自动改写 soul
- 不做 GEPA 自动进化

#### 提案 2：`mnemos-learner-nudge-trigger`

**目标**：让 learner 从“收信号”升级成“会在合适时机发起复盘”。

**当前问题**：

`LearnerBrain` 现在只会：

- 记录 signal
- 保存 candidate

但它**没有触发策略**，也没有“什么时候值得复盘”的设计。

**建议触发源**：

1. 用户明确纠正了 bot
2. 同一任务来回修了多轮
3. 任务完成且存在明显踩坑
4. 某 topic 在短时间内高频出现
5. 定时兜底批处理（低频）

**触发后的动作**：

```text
turn done
  -> classify signal
  -> if trigger matched
       enqueue review job
       review job outputs candidate
       candidate stays pending
```

**候选类型可先控制在三类**：

- `l3_profile_update`
- `skill_draft`
- `prompt_hint`

**收益**：

- 让学习脑开始“有节奏地产出”
- 不需要先把完整 P6 做完
- 与现有 spec 完全兼容

#### 提案 3：`mnemos-memory-consolidation`

**目标**：把“约束驱动提炼 / 遗忘”补进现有记忆主线。

**当前问题**：

- L1 会继续长
- L3 persona 会继续堆
- `_update_l2_summary` 仍偏占位
- 我们有 supersede，但缺少“主动合并”和“超限压缩”

**建议机制**：

1. **容量阈值**
   - topic 链长度阈值
   - L3 profile 长度阈值
   - session summary 长度阈值

2. **触发动作**
   - merge：近似重复经验归并
   - compress：长链压缩为摘要节点
   - archive：长期未命中且低重要性内容降级
   - pin：高重要性约束永不淘汰

3. **排序与遗忘原则**
   - 高 importance 常驻
   - 高 hit_count 延缓遗忘
   - 高 recency 优先保留细节
   - 低相关低命中内容允许降级

**收益**：

- 长会话 / 长期使用后不至于噪声上升
- 让“持久”真正包含“巩固 + 遗忘”
- 为 P4 benchmark 之后的长期稳定性补课

### 10.5 这三条提案和现有路线图如何衔接

```text
当前主线
P1/P2/P3/P4  =  记忆检索内核

下一阶段
P4b/P4c      =  提高记忆原子质量
P4d          =  让记忆会归并、会遗忘
P6a          =  learner 会在合适时机复盘
P6b          =  Skill 层承接“怎么做”的经验

更后面
P6 完整闭环 =  候选审核、版本演进、长期自进化
```

这里最关键的设计判断是：

- **P4b/P4c** 解决“记忆本身够不够准”
- **P4d** 解决“记忆会不会越用越乱”
- **P6a/P6b** 解决“经验能不能变成本事”

三者不是替代关系，而是先后衔接。

### 10.6 建议顺序（很重要）

#### 第一优先级：先不急着做完整 P6，先做轻量闭环

推荐顺序：

1. `P4 benchmark` 复测
2. `P4b` / `P4c`（L1 + Topic）
3. `P4d`（归并/遗忘）
4. `P6a`（Nudge 触发器）
5. `P6b`（Skill 层）
6. 完整 `P6`（审核流、版本演进、更复杂闭环）

#### 为什么不是直接冲 Skillify 全家桶

因为现在的主矛盾仍是：

- recall 还没稳到 90%
- L1 质量还有明显短板
- rerank 生产配置还没调顺

如果过早上完整 Skillify，很容易出现：

- skill 草稿质量低
- learner 候选噪声大
- token / 复杂度先爆炸

所以正确姿势是：

**先把记忆内核打磨稳，再把“执行经验”单独抬起来。**

### 10.7 明确的非目标

为避免路线发散，下面这些先明确不做：

1. **不做 Capture Everything**
   - 不全量吃邮件、书签、网页历史
   - 先把当前聊天 / 知识库 / wiki 内核打透

2. **不做重型 GEPA / RL**
   - 当前阶段只做外部知识资产演化
   - 不做模型权重内化

3. **不做复杂跨 bot Skill 市场**
   - 先 bot 内闭环，再谈共享

4. **不让 learner 自动改 soul**
   - 候选永远先 pending

## 11. 关键不变量（改造时必须守住）

1. **本地优先**：默认走本地，不强制联网。
2. **向后兼容**：老 L1 `.md` 原子缺字段要安全默认；schema 版本号 bump。
3. **可回滚**：`memory_retrieval_strategy` 仍可切回 `fts`；`embedding_provider: off` 回滚哈希。
4. **prefix cache 纪律**：stable system 不变、动态块挂 user 尾部的约定不破坏。
5. **不自动改 soul.md**：学习脑只产候选（沿用现有 spec 基线）；平台 constraints 为全局只读层，Bot 级仍用 `constraints.md` 可选覆盖人格约束。
6. **Skill 不等于记忆**：技能资产单独建模，不能继续全部压回 L1 原子。
7. **后台复盘不阻塞前台**：Nudge / learner / curator 一律异步。
