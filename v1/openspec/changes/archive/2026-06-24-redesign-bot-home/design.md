## Context

- **当前 2.0 状态**：`meclaw2/` 已精简为纯聊天 Web 应用，保留供应商、Bot、Soul、会话与流式聊天；主界面仍是传统的“左侧列表 + 右侧聊天”工具布局。
- **用户目标**：打开软件后第一眼看到的是 Bot 模块大厅，而不是会话侧栏；Bot 成为产品首页的一级实体，供应商则退回到设置中的基础设施角色。
- **现有数据约束**：Bot 数据已经存于 `config.json` 的 `bots[]`，字段包括 `name`、`avatar`、`profile_id`、`model`、`temperature`、`max_tokens`；Soul 存于 `souls/{bot_id}/soul.md`，约束已存在 `constraints.md` 但当前 2.0 UI 未暴露。
- **交付边界**：本次是 `meclaw2/` 的产品入口与配置体验重构，不涉及 1.0，也不重新引入知识、记忆、Wiki 能力。

## Goals / Non-Goals

**Goals:**

- 启动页改为 Bot 模块网格首页，支持进入、新建、编辑、删除和排序。
- 通过整理模式提供 iOS 风格的抖动反馈与拖拽排序。
- 将 Bot 编辑整合为单一弹窗，明确“Bot = 人格壳，供应商 = 大脑”的配置关系。
- 保留右上角设置里的供应商管理，但弱化设置中的 Bot CRUD 入口。
- 不破坏现有会话、Soul、供应商与流式聊天闭环。

**Non-Goals:**

- 不重做聊天页内部的消息协议或会话持久化格式。
- 不恢复 Knowledge / Memory / Wiki 模块。
- 不把供应商新增流程直接塞进 Bot 编辑弹窗内。
- 不为 1.0 产物提供兼容层或迁移逻辑。

## Decisions

### 1. 产品信息架构改为“首页 Bot 大厅 → Bot 聊天工作区”

启动应用后默认展示 Bot 网格首页，而不是直接进入聊天页。用户点击某个 Bot 模块后，才进入该 Bot 的会话与聊天界面。

这样做的原因：
- 更符合用户要的“映入眼帘是几个大的模块，每个模块对应一个 Bot”。
- 让 Bot 成为明确的产品入口，而不是埋在设置或侧栏里的配置项。
- 为后续继续做更强的 Bot 品牌感、封面感、分组感留空间。

备选方案：
- 保持当前侧栏结构，只把 Bot 行做大。放弃原因：视觉层级仍是工具式列表，不满足首页感。

### 2. 首页网格包含固定的 `+` 模块，且 `+` 不参与排序

Bot 首页按网格展示全部 Bot，最后一个固定卡片为 `+`，用于新建 Bot。排序模式下只允许拖动真实 Bot 卡片，`+` 卡片始终固定在尾部。

这样做的原因：
- 与移动端图标网格心智一致。
- 保证新增入口稳定，不会因为排序而跑位。

备选方案：
- 把「新建 Bot」放在顶部按钮。放弃原因：弱化了首页模块化语言，也与用户描述不符。

### 3. 编辑/删除按钮常驻，整理模式只负责“抖动 + 拖拽排序”

每个 Bot 卡片默认就显示编辑与删除操作；用户点右上角“整理”后，卡片进入抖动状态，并允许拖拽排序。整理模式不是操作入口切换，而是排序专用模式。

这样做的原因：
- 用户明确要求“每一个模块旁边都有一个删除按钮和编辑按钮”。
- 排序是低频行为，用模式切换承载更合理；编辑/删除是常规管理动作，不应被藏得太深。

备选方案：
- 仿 iOS 只在抖动时显示删除。放弃原因：不符合本次明确交互要求。

### 4. Bot 顺序直接以 `config.json` 中 `bots[]` 数组顺序为准

前端排序完成后，将新的 Bot 顺序直接持久化到 `bots[]` 数组，而不是新增单独的 `sort_order` 字段。

这样做的原因：
- 当前 2.0 数据模型简单，数组顺序天然就是展示顺序。
- 后端改动最小，读取列表时无需额外排序逻辑。

备选方案：
- 给每个 Bot 增加 `position` 字段。放弃原因：会引入额外同步与去重问题，当前收益不高。

### 5. Bot 编辑弹窗分为“基础信息 / 大脑 / 人格 / 高级参数”

Bot 编辑弹窗至少展示：
- 名称
- 头像
- 供应商选择（绑定哪个 `profile_id`）
- 模型覆盖（可空）
- `temperature`（可空）
- `max_tokens`（可空）
- Soul 文本
- Constraints 文本（可空）

同时展示供应商状态信息，例如当前绑定供应商名称、模型、是否已配置 API Key；若没有任何供应商，弹窗应提示先去设置中新增供应商。

这样做的原因：
- 这些字段正好对应现有 2.0 Bot / Soul 能力与真实聊天行为。
- Soul 和约束都属于“人格层”，应该与 Bot 编辑强绑定，而不是继续散落在 prompt 或单独简陋入口里。

备选方案：
- 仅保留名称、头像和供应商，Soul 仍用单独 prompt。放弃原因：配置入口割裂，不符合“点编辑后看到名字、灵魂文件之类”的要求。

### 6. 供应商仍只在设置中管理，Bot 弹窗只做选择，不做供应商 CRUD

设置页继续保留供应商增删改查与连接测试；Bot 编辑弹窗只允许从现有供应商中选择一个作为大脑，不直接创建或编辑供应商。

这样做的原因：
- 避免同一类基础设施配置在两个入口重复维护。
- 让“先建供应商，再给 Bot 绑定大脑”的链路更清晰。

备选方案：
- 在 Bot 弹窗中内嵌“新增供应商”。放弃原因：配置面板会迅速变重，职责混乱。

### 7. 允许未绑定供应商的 Bot 存在，但必须显式显示“未配置大脑”

Bot 仍可先创建为草稿状态，不强制必须立刻绑定供应商；但首页卡片和编辑弹窗都必须明确显示未绑定状态，且未绑定 Bot 不可直接进入可发送消息的聊天状态。

这样做的原因：
- 与现有后端兼容，不强制破坏已存在的 Bot 数据。
- 仍然保留先做人设草稿、后补供应商的灵活性。

备选方案：
- 创建 Bot 时强制必须选择供应商。放弃原因：对草稿型使用流程过于刚性。

### 8. 聊天页保留现有会话能力，但增加“返回 Bot 首页”

进入某个 Bot 后，聊天工作区仍保留该 Bot 的会话列表与消息流，但顶层导航不再是 Bot 侧栏，而是提供一个清晰的“返回 Bot 首页”入口。

这样做的原因：
- 首页承担选 Bot，聊天页承担用 Bot。
- 降低 Bot 切换与会话切换混在一个列表里的认知负担。

备选方案：
- 进入 Bot 后直接隐藏会话列表，只保留单对话。放弃原因：会削弱 2.0 现有的多会话价值。

## Risks / Trade-offs

- **[首页与聊天页切换层级变深]** → 通过明显的返回入口和保留会话列表，减少迷失感。
- **[排序模式增加前端状态复杂度]** → 将其限制为单一 `isArrangeMode` 状态，并在退出时统一保存顺序。
- **[Soul + Constraints 同屏编辑会让弹窗变长]** → 采用分组布局或折叠高级区，优先保证主信息可见。
- **[未绑定供应商的 Bot 容易让用户困惑]** → 首页卡片与编辑弹窗都显示“未配置大脑”，并禁用发送链路。

## Migration Plan

1. 复用现有 `bots[]`、`souls/{bot_id}/soul.md` 与 `constraints.md` 数据，不做结构迁移。
2. 首次上线新版首页时，Bot 网格顺序直接继承现有 `bots[]` 顺序。
3. 若旧 Bot 没有 `constraints.md`，按空字符串处理并在保存时按需创建。
4. 如果排序持久化接口上线后出现问题，可回退到只读首页网格，不影响已有 Bot 与聊天数据。

## Open Questions

- 首页 Bot 模块是否需要展示最近一条会话摘要，还是只展示名称/头像/供应商状态即可。
- 聊天工作区的会话列表最终放左侧、顶部 Tab，还是抽屉式入口；本次提案先只锁定“首页先选 Bot”的一级结构。
